# apps/api rules

Root rules ([AGENTS.md](../../AGENTS.md)) apply. Endpoint reference: [docs/API.md](../../docs/API.md); testing: [docs/TESTING.md](../../docs/TESTING.md); secrets design: [docs/SECRETS.md](../../docs/SECRETS.md).

## Layout (today)

- `src/<module>/` per feature: `settings` (`registry/` manifests and the data migration; the routes are the platform's), `secrets` (+ `secrets/export`: zip, README and HTML renderers), `secret-types`, `backups` (admin `admin/backups`, user `backups/me`; `jobs/` the two handlers, `backup-queue.service.ts`, `backup-runner.service.ts`, `backup-archive.service.ts`, `backup-schedule.task.ts`), `media`, `ai` (card extraction `card-extract.*`, the `GET /ai/status` alias and the `vault:migrate-ai-platform` data step; the AI slice itself is bound in `platform/ai/`), `common` (decorators, `CryptoService`, logger, schemas), `prisma`, plus the platform bindings `platform/` (host ports, host core, About, `platform/credentials/` (the credential store), `platform/identity/`: the identity slice and its host ports, `platform/jobs/`: the queue, the worker-node fleet and their host ports), `platform/storage/` (the storage slice: `StorageModule.forRoot`, `StorageConfigModule`, the key-prefix manifest, the one-time env import), `platform/exports/`, `platform/user-data/`, `platform/onboarding/` (the exports, user-data and onboarding slices, E9.3), `doctor/` (the Doctor binding and Vault's three checks) and `openapi/`, `app-registrations/` (error codes, Vault's permissions, user-owned models, model ownership: `registrations.ts` is imported first by `main.ts`, `app.module.ts` and the test setup).
- `prisma/schema/` is **generated** (never hand-edit): `npm run db:compose` composes the `@marinoscar/platform-db` fragments with `prisma/fragments/*.prisma` (Vault's own models: `vault.prisma`, `media-folder-files.prisma`). `prisma/migrations/` holds Vault's seven original migrations, the 38 installed platform copies (0003 to 0040, byte copies proven by `prisma/platform.lock`) and `20261102130000_add_media_folder_files`; `prisma/platform.lock` lists the deviations from the platform history and the app's raw-SQL index. `scripts/baseline-deviations.mjs`, `scripts/baseline-rehearsal.sh` and `scripts/verify-vault-data.ts` serve the baseline runbook ([database-baseline](../../docs/runbooks/database-baseline.md)); `prisma/seed.ts` and `system-secret-types.ts` seed roles, permissions and the system secret types. `test/` holds Jest specs (`test/jest.config.js`); `src/**/*.spec.ts` sit beside the code.
- **Platform bindings:** storage (E6.1) and settings (E4.1) are `src/platform/<slice>/` bindings of `@marinoscar/platform-api`; AI, notifications and db-backup follow (E7 to E9). Identity (sign-in, sessions, users, roles, allowlist, PATs, device flow, test login) is the platform's since E3.2. **Object storage is runtime configuration** (`/admin/settings/storage`, the `storage` system setting plus the credential `storage/default`): never add a storage environment variable. A new writer of object keys registers its prefix in `platform/storage/storage-key-prefix.manifest.ts` (or the purge misses it) and injects `STORAGE_PROVIDER` / the platform `ObjectsService` from `@marinoscar/platform-api/storage`; the legacy `STORAGE_PROVIDER` / `S3_*` / `AWS_*` variables are imported once ([runbook](../../docs/runbooks/storage-config-migration.md)). `src/prisma/default-org.ts` stays for the domain services that read `storage_objects` (`PLATFORM-ADOPTION-SHIM(multi-org)`, [local-exceptions](../../docs/platform-adoption/local-exceptions.md)). Domain modules (secrets, secret-types, backups, media, card extraction) stay in `apps/api/src` until E12. Classification: [module-classification](../../docs/platform-adoption/module-classification.md).

## Rules

- **Every route declares `@Auth(...)` or `@Public()`** from `@marinoscar/platform-api/identity` with the exact permission (`PERMISSIONS.*` in `src/common/constants/roles.constants.ts`, derived from the platform's and `app-registrations/permissions.ts`). A route with bare `@Auth()` is ownership-scoped (`/api/ai/status`, `/api/storage/objects`). Add the route to `ROUTES` in `test/rbac/vault-rbac-matrix.integration.spec.ts` (a coverage test fails otherwise). Roles: `admin` is the one SYSTEM role (`user_roles`); `org_admin`, `contributor`, `viewer` are ORG roles on the default-organization membership, and `secrets:*`, `secret_types:*`, `media:*` are org-scoped (the `*_any` ones are system, `admin` only). A new permission is declared in `app-registrations/permissions.ts` and reaches the database through `npm run prisma:seed` (which composes the catalog from `src/platform/permissions.ts`).
- **Validate input with Zod** DTOs; annotate OpenAPI/Swagger; update [docs/API.md](../../docs/API.md) and `docs/DOMAIN-REFERENCE.md` when an endpoint changes.
- **Adding an endpoint**: controller method (auth/RBAC decorators), service method (all business logic), OpenAPI annotations, unit + integration tests, API docs.
- **Responses** are `{ data, meta? }` (the platform host envelope); errors `{ statusCode, code, message, details?, timestamp, path }` from the platform `HttpExceptionFilter`, which keeps an application `code` only if it is registered in `app-registrations/error-codes.ts` for the status. The deliberate exceptions return a raw streamed zip: `POST /api/secrets/export` and `POST /api/admin/backups/export`; they take `@Res()` (no passthrough) and `reply.send(stream)`, because the platform envelope wraps a `StreamableFile`.
- **Host and Doctor**: `/api/health*`, `/api/admin/maintenance`, `/api/admin/doctor`, `/api/admin/about` and `/api/docs` (Scalar) are the platform's. A new health indicator is `registerHealthIndicator`; a new Doctor check is a read-only provider in `doctor/checks/` registered in `DoctorChecksModule` (the kit `describeDoctorCheckConformance` proves it). **Settings** (E4.1): `/api/system-settings`, `/api/user-settings` and `/api/org-settings` are the platform slice's (`platform/settings/settings.config.ts`, `systemRowKey: 'global'`). A new setting is a namespace declared in `app-registrations/settings.ts` and listed there (append, never insert; the key is camelCase, never dotted, never secret-named: a secret is a credential); read it with `SystemSettingsService.getNamespace('key')`, never from the row. `ui` and `features` keep their legacy keys on purpose; `ai` is the platform AI slice's namespace extended with `cardExtractModel` (E8.1). The AI key never enters a namespace: it is the platform's deployment credential, set through `/api/admin/ai/*`. `npm run vault:migrate-settings` ([runbook](../../docs/runbooks/settings-migration.md)) rewrites pre-E4.1 user profiles.
- **Secrets and crypto**: encrypt and decrypt secret values only through `CryptoService` (`VAULT_ENCRYPTION_KEY`). Runtime-configured keys (today the OpenAI key, purpose `ai`, name `openai`) live in the platform credential store (`CredentialsService`, `SECRETS_ENCRYPTION_KEY`, bound in `src/platform/credentials/`); a different key, never mixed with `VAULT_ENCRYPTION_KEY` (`test/credentials/vault-key-separation.spec.ts`). `npm run vault:migrate-ai-key` moves a pre-E4.2 key ([runbook](../../docs/runbooks/ai-key-migration.md)). Never log, return or put in an error/span/audit payload a decrypted value, backup password or AI key. List responses are not decrypted (keep it so). A rotated or missing key must fail loudly (see `backup-password.ts`), not fall back.
- **Secret versions**: a data change writes a new immutable `secret_versions` row and flips `isCurrent` in one transaction; exactly one current version. Attachments are version-scoped; delete by refcount (see root invariants and [SECRETS.md](../../docs/SECRETS.md)).
- **Backups**: the archive password is used in memory or stored encrypted, never logged. Backups are the server-only queue jobs `vault.backup.run` (system, `orgId` null) and `vault.user_backup.run` (`subjectType 'user'`) since E5.2 (#82): the routes queue through `BackupQueueService` (job row and `backup_runs` row in one transaction; the queue's dedup key is the "already running" check, a conflict is `409`; never add an advisory lock), `BackupScheduleTask` is the enqueue-only minute tick, the handlers in `backups/jobs/` run `BackupRunnerService`, and `BackupArchiveService` builds the zip. A user archive password reaches the handler only as `CryptoService` ciphertext in `jobs.payload` (removed when the run settles), decrypted in memory, never logged. Dumps and archives stream; never buffer ([local-exceptions](../../docs/platform-adoption/local-exceptions.md#e52-backups-as-queue-jobs-done)).
- **AI**: Vault has no provider code. AI is the platform slice, configured once in `src/platform/ai/ai.config.ts` (`AiModule.forRoot`, `providers: ['openai']`, feature `card_extract` in `app-registrations/ai.ts`, the model from `ai.cardExtractModel` via `VaultAiTargetResolver`). Card extraction (`src/ai/card-extract.*`) calls `AiService.forUser(userId, { orgId, feature: 'card_extract' })`; it persists nothing, never requests the CVV (the normalizer strips it) and sits behind `AiEnabledGuard` + `ai:use` + `secrets:write`. Never import a provider SDK (suite `ai-no-sdk-leak`); the budget is the platform cap `ai.limits`. `test/ai-conformance.spec.ts` boots the platform AI suites; `test/ai/card-extract.db.spec.ts` is the end-to-end proof over a fake provider.
- **Prisma** (v7, driver adapter `@prisma/adapter-pg`; config in `prisma.config.ts`, datasource URL not in the schema): use `npm run prisma:*`, never bare `npx prisma`. Never edit an existing migration (comments count). Partial/expression indexes are hand-written SQL, intentional drift. Schema work goes to `database-dev`.
- **Long-running work is a queue job** (root rule, IN FORCE since E5.1/E5.3, #81/#83): the queue is `platform/jobs/` (`JobsModule.forRoot`, `NodesModule.forRoot`); a `@Cron` only calls `enqueueHousekeepingJob` and a handler (self-registering, with a `label` and a `profile`, `orgId` explicit) does the work; every Vault job type is server-only (no `nodeResultSchema` / `persistNodeResult`). Pin a new type string in `test/jobs/job-type-snapshot.spec.ts` (permanent once rows exist). There is no inline `@Cron` / `@OnEvent` shim left since E6.1 (the storage sweep and post-upload processing are the platform's jobs): `CRON_EXEMPTIONS` and `LISTENER_EXEMPTIONS` in `test/jobs/cron-source-roots.ts` are empty, enforced by `test/conformance.spec.ts` (`cron-enqueue-only`) and `test/jobs/on-event-no-io.spec.ts`; a new timer or listener is not a new exemption. In-memory bookkeeping is not work: the AI burst limiter prunes lazily on `consume`, with no timer. Jobs tests boot with `JOBS_WORKER_MODE=off` (`test/setup.ts`); a real-database test that needs the worker sets `JOBS_WORKER_MODE=all` itself. **`notify()` after commit** (E7.1/E7.2: the runner notifies after the `backup_runs` update, never inside a `$transaction`); platform-owned behaviour is requested by a seam issue on EAB, never copied locally.
- **Exports, user data and onboarding** (E9.3, #91): three platform slices bound in `platform/{exports,user-data,onboarding}/`. **No platform export ever carries a secret value or ciphertext**: `Secret` and `SecretVersion` stay `export: 'exclude'` in `app-registrations/user-owned-models.ts`, secret metadata (names, types, timestamps, counts) leaves through the `vault-secrets` source, which copies NAMED columns only (never `...row`); values leave only through `POST /api/secrets/export`. Prove any change with `test/exports/platform-export-secrets.db.spec.ts` (markers in the decrypted value and the ciphertext). **A new model with a `User` foreign key needs a keep-or-delete decision** in `platform/user-data/user-data.manifest.ts` (the `userData` conformance suite fails otherwise) and an export policy in `user-owned-models.ts`; a deleted model whose bytes are not `storage_objects` rows (backup archives) needs a delegate job (`vault.user_data.purge`) that deletes the bytes before the row; the factory reset's own steps are `platform/user-data/factory-reset.steps.ts`. The reset summary needs the `required-field-filters.ts` shim (local-exceptions). New onboarding step: ids are permanent, `evaluate` is pure over facts (`platform/onboarding/onboarding.facts.ts`), `permission` is the exact string of the page it links to; the manifest is registered from `app-registrations/registrations.ts` (after the permissions). Runbook: [factory-reset](../../docs/runbooks/factory-reset.md).
- **Email and notifications** (E7.1): `platform/email/email.config.ts` and `platform/notifications/notifications.config.ts` mount `EmailModule.forRoot` (NOT global: import the one `emailModule` object), `NotificationsModule.forRoot` (global) and `BroadcastsModule`. The registries are filled by `platform/notifications/notification.manifest.ts` BEFORE the modules compose (platform channels, rendering context, platform templates, then the events); Vault's events live in `notifications-registry/` (`vault.notifications.ts`: `vault.backup_succeeded`, `vault.backup_failed`, `vault.card_expiring`; an event key is `<domain>.<name>`, one dot only) and its own templates in `email-templates/` (E7.2, #86). Backup results are raised by `backups/backup-notifier.service.ts` from the runner's settle points; card expiry by the server-only job `vault.cards.expiry_scan` (`card-expiry/`), deduplicated by an `audit_events` row, with a payload that never holds a card number, CVV or field value. Layout: `THEME_COLOR` of `packages/shared/identity.json` and the committed `assets/email/logo.png` (the Dockerfile copies `assets/`). SMTP, SES and VAPID are runtime-configured in the admin UI: **never add an environment variable for them**. A new permission-bearing slice is added to `slices` in `platform/permissions.ts` (`notifications` brings `broadcasts:*`, `push:*`, `org_broadcasts:*`; run `npm run prisma:seed`). Event keys, channel ids and template names are persisted: add, never rename. New notification: the [add-notification skill](../../.claude/skills/add-notification/SKILL.md).
- **A behaviour change carries tests** in the same or the next commit.

Run: `npm test`, `npm run typecheck`, `npm run test:cov` (all from `apps/api`).

# apps/web rules

Root rules ([AGENTS.md](../../AGENTS.md)) apply. This file is what to get right when editing the React app. Target UX: [docs/specs/ux-refresh.md](../../docs/specs/ux-refresh.md).

## Layout

- **The host** (E12.3, #104): the Vault domain pages, components and hooks (secrets, secret types, cards, media, Home, backups, the General / Profile / Appearance card pages), `destinations`, the brand tokens and themes and `BrandLockup` live in `@marinoscar/vault-web` (`packages/vault-web`, [README](../../packages/vault-web/README.md)); `src/` keeps `App.tsx` (routes, lazy imports from `@marinoscar/vault-web/<slice>/ui`), `main.tsx`, `services/api.ts` (builds the client and calls `configureVaultWeb`), `platform/`, `identity/`, `config/` (registries, `shell.ts`, `settingsFeatures.ts`), `components/common/Layout.tsx`, the platform-page slots and the hub bindings. A domain page or component is written in the package, never here: `__tests__/config/packagesFirst.test.ts` fails otherwise. The layout notes below predate the move; read a domain path as the package's.
- `src/pages/` (HomePage, SecretsPage, SecretDetailPage, Create/EditSecretPage, CardsPage, ImportCardPage, RenewCardPage, SecretTypesPage and editors, Media* pages, UserSettingsHubPage, TestLoginPage, `settings/` (the per-user card pages), `admin/` (the Console hub and its card pages)), `src/identity/` (the identity slice's binding: `IdentityProviders.tsx`, `identityAdapters.ts`, `LazyIdentityDataTable.tsx`, `LoginPage.tsx` with the brand slots), `src/components/` (`admin`, `brand` (`BrandLockup`), `cards`, `common` incl. `Layout.tsx`, `home`, `media`, `secret-types`, `secrets`, `settings`, `user`), `src/config/` (`destinations.ts`, `shell.ts`, `adminSections.tsx`, `userSettingsSections.tsx`, `settingsFeatures.ts`), `src/platform/` (`platformHost.tsx`: the `PlatformHostProvider` every packaged page reads), `src/hooks/`, `src/services/api.ts` (the platform's `PlatformHttpClient` plus Vault's domain calls), `src/theme/` (`tokens.ts`, `contrast.ts`, `index.ts`), `src/assets/brand/`, `src/utils/`, `src/types/`.
- Routes live in `src/App.tsx`. Tests: `src/__tests__/` (**Vitest** + React Testing Library; `components/`, `config/`, `hooks/`, `pages/`, `services/`, `theme/`, `utils/` (incl. `viewport.ts` to size the window for the shell), `mocks/`, `setup.ts`).
- **The shell is the platform's** (`@marinoscar/platform-web@0.1.0-next.21`, E10.1/E10.2, #92/#93): `App.tsx` mounts `ShellRoot` (Vault themes, light / dark / system), `IdentityProviders` and `VaultPlatformHostProvider`. No `ShellPreferencesProvider` or `DataTablePreferencesProvider` is mounted (#153): the rail collapse and every table layout take the platform defaults, stored in the `navigation` and `dataTables` namespaces of `/api/user-settings` through the host's client; never re-add a `localStorage` port. `components/common/Layout.tsx` is a thin `ShellLayout` binding. Identity UI, settings hub, datatable and AI pages come from the platform in E3 to E10.3+; domain pages (secrets, cards, media, backups UI) stay here until E12.
- **Identity is the platform's** (E3.3, #78): the session is the packaged `AuthProvider` over `services/api.ts` (the platform's `PlatformHttpClient`; the access token lives only there, the refresh token in the HttpOnly cookie); routes use the packaged `RequireAuth` / `RequirePermission`, components `useAuth` / `usePermissions` from `@marinoscar/platform-web/identity/headless`. `/login` is the packaged `LoginPage` with Vault's mark and tagline in its `Logo` / `Title` slots (`identity/LoginPage.tsx`); `/auth/callback`, `/activate`, `/settings/tokens` and `/admin/settings/users` render the packaged `AuthCallbackPage`, `ActivateDevicePage`, `UserTokensPage` and `UsersPage`. The identity cards ship as data (`identityAdminSections.access`, `identityUserSettingsSections.security`) and are spread into the registries in place. Never re-add an app copy of these pages; a gap is a seam request on EnterpriseAppBase (to add a tab to Users & Allowlist, use `slots.Tabs`).
- **AI** (E8.2, #88) is the platform's: `platform/aiConfig.tsx` (`VaultAiConfigProvider`, the shared `GET /api/ai/config`, fetched only once signed in) sits above `VaultPlatformHostProvider` in `App.tsx`, `AiWebAdaptersProvider` hands the AI pages Vault's spinner (`platform/aiAdapters.ts`), and `config/settingsFeatures.ts` registers the `ai` feature from it. The Console's `AI` card (`ai_config:read`, no `feature`) is the packaged `AiConfigPage` with Vault's `components/settings/CardScanModelSection.tsx` (`ai.cardExtractModel`, saved through `PATCH /api/system-settings`) in its `AfterContent` slot; `AI models` and `AI usage` (`ai_config:read`, `feature: 'ai'`, routes behind `RequireAiEnabled`) are the packaged pages at `/admin/settings/ai/models` and `/ai/usage`. There is no AI key field anywhere else and no verify call: keys are set on the packaged page (`/api/admin/ai/*`). Card scanning is offered only when `GET /api/ai/config` passes `isCardScanAvailable` (AI on, key policy `byok_with_org_fallback`, the `openai` provider enabled with `hasOrgKey`; the server's rule in `packages/vault-api/src/ai/card-scan-availability.ts`) and the viewer holds `ai:use` (`useAiStatus` of `@marinoscar/vault-web/core/headless`, reading the shared `VaultAiConfigProvider` copy).
- **Storage** (E6.1 web follow-up, #84) is the platform's runtime configuration, never environment variables: the Console's `Storage` card (last in Administration, `storage_config:read`, the exact string of the platform storage-config controller; no `feature`) is the packaged `StorageConfigPage` (`@marinoscar/platform-web/storage/ui`, lazy, no adapters) at `/admin/settings/storage`; writes need `storage_config:write`, gated inside the page. A "storage is not configured" hint links there with `components/common/StorageSettingsLink.tsx` (rendered only for `storage_config:read`); never tell a user to set `S3_*` or `STORAGE_PROVIDER`.
- **Exports, user data and onboarding** (E9.3, #91) are the platform's pages with Vault's notices: `pages/DataExportRoute.tsx` (Download your data; the notice says the downloads carry no secret value and links to My backups), `pages/UserDataPages.tsx` (`DangerZoneRoute`, `FactoryResetRoute`, notices in `components/user-data/DangerZoneNotices.tsx`), `components/onboarding/{GettingStartedRoute,SetupGuideRoute}.tsx` (refresh the checklist on mount). `Layout.tsx` wraps the shell in `OnboardingProvider` and mounts `WelcomeDialog` once. Cards: `Getting started` (Account), `Download your data` (Data), `Delete my data` (the LAST group, `Danger Zone`), `Setup guide` (Administration), `Factory reset` (the LAST admin group, `system:factory_reset`, Admin only). `__tests__/config/platformPages.test.ts` checks each descriptor is one card and one route with the controller's permission and that both Danger Zone groups stay last; a new test mock must answer `GET /api/onboarding` (`mocks/handlers.ts` does, with the welcome already seen).
- **Notifications** (E7.2) are the platform's: `src/platform/notifications.ts` configures the slice once (`configureNotificationsWeb`, imported by `main.tsx`; tests configure it in `__tests__/setup.ts` without SSE, and `mocks/handlers.ts` serves an empty inbox), `Layout.tsx` wraps the shell in `NotificationProvider` and puts `NotificationBell` in `ShellAppBar`'s `actions`; the Email, Web Push, Broadcasts and Notifications cards render the packaged pages (`@marinoscar/platform-web/email/ui`, `/notifications/ui`). No push subscription sync until a built service worker exists (local-exceptions). Identity UI, settings hub, datatable and AI pages come from the platform in E3 to E10.3+; domain pages (secrets, cards, media, backups UI) stay here until E12.
- **Database Backup** (E9.1, #89) is the platform page, not Vault's `Backups` page: `pages/admin/DbBackupSettingsPage.tsx` renders the packaged `DbBackupPage` (`@marinoscar/platform-web/db-backup/ui`) inside `DbBackupWebAdaptersProvider` with `platform/dbBackupAdapters.tsx` (the lazy platform `DataTable` and one `createDbBackupApi(vaultPlatformApi)`, built once). Its Operations card is `dbBackupAdminSections.operations[0]` spread in `config/adminSections.tsx` with a Vault description that says it is NOT the encrypted secret backups; the route `/admin/settings/db-backup` and the card gate on `db_backup:read` (what `DatabaseBackupController` enforces on its reads; writes need `db_backup:write`, restore and rollback `db_backup:restore`, disabled inside the page, never hidden). `db_backup:read` is in the Console hub's any-of gate (`App.tsx`, `config/destinations.ts`). Do not rename the card to `Backups` or merge the two pages.

## Stack

React 19, MUI 9 (`@mui/material`, `@mui/icons-material`), react-router-dom 7, Vite 8, Vitest 4 + React Testing Library 16 + jsdom 29, aligned with the peer dependencies of `@marinoscar/platform-web` (E1.3, #70). MUI 9 conventions:

- No system props on `Box`, `Stack`, `Typography`, `Grid`: put `color`, `fontWeight`, `display`, `alignItems` and friends in `sx`. `Typography` has no `paragraph` (use `sx={{ marginBottom: '16px' }}`).
- `Grid` is the v2 API: `<Grid size={{ xs: 12, md: 6 }}>`, no `item`, no `xs`/`md` props.
- Slot props, never the removed `*Props`: `slotProps.input`/`htmlInput`/`inputLabel`/`select` on `TextField`, `slotProps.primary`/`secondary` on `ListItemText`, `slotProps.paper` on `Menu`.
- `*Outline` icons are gone: use `*OutlineOutlined` (same glyph; `*Outlined` is the filled one).
- A `Switch` has the ARIA role `switch`, not `checkbox`; query it with `getByRole('switch', ...)`.
- Tests: an MSW handler must not call `request.formData()` on an upload (undici cannot read a jsdom `File`); spy on `FormData.prototype.append` instead (see `ImportCardPage.test.tsx`).

## Rules

- **Settings UI** (root rule, in force since E10.3): a new settings page is a card appended to `ADMIN_SECTIONS` or `USER_SETTINGS_SECTIONS` plus a route under `/admin/settings/*` or `/settings/*` wrapped in `RequirePermission` with the card's exact permission (the API controller's string), never a tab; both hubs are bindings of the packaged `SettingsHub`, never forked. Card pages use `components/settings/SettingsPageFrame.tsx`. `__tests__/config/settingsRegistry.test.ts` checks the registries against `App.tsx` and the API's permission constants. Recipe: [`add-settings-page` skill](../../.claude/skills/add-settings-page/SKILL.md).
- **Breakpoint gates**: the five coupled gates all sit at `sm` (600px), never `md`, and they are the platform shell's. The app reads no breakpoint for them: `__tests__/config/breakpointGates.test.ts` fails on any `useMediaQuery(` or `breakpoints.up|down|between|only(` in `src/` not listed there with a reason (a domain page adapting its own content may be listed; navigation chrome never).
- **Navigation**: destinations are declared once in `src/config/destinations.ts` (`DESTINATIONS`, `DESTINATION_ROUTES`, `UNOWNED_ROUTES`) as `ShellDestination`s and bound in `config/shell.ts`; Home, Secrets, Cards, Media are non-pinned; Settings and Console are `pinned` (a mode, not a peer) and never on the bottom bar (`BOTTOM_BAR_NAVIGATION`); at most **four** non-pinned. A new route must be owned by exactly one destination (or listed in `UNOWNED_ROUTES`): `__tests__/config/destinations.test.ts` reads `App.tsx` and fails otherwise. A destination's `permission` / `anyPermission` is the exact controller string.
- **Brand**: colours live only in `src/theme/tokens.ts` (`BRAND_TOKENS`); `theme/index.ts` feeds them to `createShellTheme`. Amber (`accent`) is a fill, never text on a light surface (use `accentText`). Changing a token keeps `__tests__/theme/tokens.test.ts` (WCAG ratios from spec section 5) green. Read the theme through `useTheme()`/`sx` palette keys; the light / dark choice through `useShellTheme()` / `useOptionalShellTheme()` of `@marinoscar/platform-web/shell/headless` (there is no app `ThemeContext`).
- **The UI presents; the API authorizes.** Hiding a card or button is not security. Gate with the packaged `usePermissions` / `RequirePermission` using the same permission strings as the controllers.
- **Never keep secret values longer than needed**: list responses are not decrypted, so values come only from the detail view; copy through `useCopyToClipboard`; never put a value in `localStorage`, logs or error reports. Backup passwords are held in component state only and never persisted.
- **Never call an AI provider from the browser**; card scanning goes through `POST /api/secrets/cards/extract` and shows `AiEgressNotice`. The CVV is never sent, never returned (`cvv`/`security_code_2` are always null) and never seeded into the review form. Map failures in `describeCardExtractionError` (`hooks/useCardImport.ts`): `403` with `details.reason: 'AI_DISABLED'` is "AI is off — an admin can turn it on in Console → AI", `503 AI_NOT_CONFIGURED` is "AI is not set up yet", any other `403` is a missing `ai:use`; the Console link only for `ai_config:read`.
- Use MUI theming (`src/theme/`) and the responsive layout; no hard-coded colours outside `theme/tokens.ts`. Brand tokens are specified in `ux-refresh.md` section 5.
- Tests render through `__tests__/utils/test-utils.tsx` (`ShellRoot` + a fixed platform identity `AuthContext` value + the identity adapters + `VaultPlatformHostProvider`, no preferences provider, so the rail and tables read and write `/user-settings` through the MSW handlers; `__tests__/platform/userSettingsPreferences.test.tsx` pins it); a test that mocks `useAuth` spreads `AUTH_CONTEXT_DEFAULTS`, and one that mocks `usePermissions` mocks `@marinoscar/platform-web/identity/headless` partially (`importOriginal`). `__tests__/identity/identityWiring.test.tsx` covers the binding; to test the shell at a width call `setViewportWidth(390 | 1440)` from `utils/viewport.ts` and `restoreViewport()` after.
- **Telemetry** (E9.2, #90): the three packaged pages (`@marinoscar/platform-web/telemetry/ui`) are the `Observability` section of `ADMIN_SECTIONS` (`telemetryAdminCards`; `telemetry:read` for the settings page, `telemetry:query` for the Explorer and Dashboard, which carry `feature: 'telemetry'`) with lazy routes in `App.tsx`. `AppTelemetryConfigProvider` (`platform/TelemetryConfigBinding.tsx`) sits ABOVE the platform host (it feeds the `telemetry` settings feature registered in `config/settingsFeatures.ts`); `platform/telemetryAdapters.ts` hands the pages the spinner and the assistant's two AI hooks over the platform AI slice (`useAiConfig`, `useAiModels`). Themes pass through `withTelemetryTokens`. `__tests__/config/telemetryParity.test.ts` holds web/API permission parity. Vault's own dashboard group needs no web code. Guide: [docs/telemetry.md](../../docs/telemetry.md).
- Runtime-configured features (storage, AI, SMTP, VAPID) are admin-UI settings, never build-time variables.
- Write components and hooks with tests; a behaviour change carries its tests in the same or next commit. Tests use invented data (placeholders, test PANs).

Run (from `apps/web`): `npm run test:run`, `npm run typecheck`, `npm run typecheck:test`, `npm run build`.

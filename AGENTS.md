# AGENTS.md

Shared rules for AI assistants working on this codebase (loaded by OpenCode, and by Claude Code through `CLAUDE.md`). Area rules live in nested `AGENTS.md` files: `apps/api`, `apps/web`, `apps/cli`. How the tools share files: [docs/AI-ASSISTANTS.md](docs/AI-ASSISTANTS.md).

## Project overview

Vault is a secrets vault: typed, versioned, AES-256-GCM-encrypted secrets (logins, API keys, payment cards, notes), card scanning with an admin-configured vision model, media folders, encrypted backups (admin schedule, user "My backups", raw-zip exports), OAuth sign-in with an email allowlist, RBAC, personal access tokens, device authorization and a CLI.
Current stack: Node 24, NestJS 11 on Fastify, Prisma 7, PostgreSQL, React 19 + MUI 9 + Vite 8, Jest (API), Vitest + React Testing Library (web), OpenTelemetry + Uptrace + Pino, Docker Compose, Nginx same-origin.
**Target** (program epic #54, children E0 to E12): the `@marinoscar/platform-*` packages from EnterpriseAppBase (EAB), Node 24, Prisma 7, React 19 + MUI 9, the `vault` CLI on `createCli`, then `@marinoscar/vault-*` domain packages. Plan, classification and exceptions: [docs/platform-adoption/README.md](docs/platform-adoption/README.md). Sections below marked **TARGET** apply as soon as their epic lands and are the rule for new work now where stated.
Start at [README.md](README.md) and [docs/README.md](docs/README.md) (index with a "Doc map by task").

## MANDATORY: No real people, companies or user material

- **Never reuse material a user shares** (documents, notes, screenshots, card photos, exported backups) anywhere in the repo, issues, PRs or commits.
- **No real people, companies, organizations or products as examples.** Use invented placeholders (`Person A`, `Org Alpha`, `Product X`, `@example.test`). Card numbers in fixtures are well-known test PANs, never a real card. Exempt only: named vendor integrations (OpenAI, Google OAuth, S3) and legal/authorship metadata.

## MANDATORY: Issue-Driven Development

Every feature and bug fix is tracked by a GitHub issue, filed **before** implementation planning is finalized (features) or the fix starts (bugs), and before any worktree or branch is created. `gh issue create` inside the repo infers the repository.

- **New feature**: `gh issue create --template feature_request.yml` (real problem, solution, component, priority; no placeholders). **Larger initiative**: `--template epic.yml`; child issues reference the epic. The platform migration is epic #54 (E0 to E12).
- **Bug fix**: `--template bug_report.yml` (reproduction, expected vs. actual, component, logs). Reuse an existing issue; never file a duplicate.
- **Platform gap seen from Vault** (an extension point the packages lack): `--template seam_request.yml`, filed on **marinoscar/EnterpriseAppBase** (`gh issue create -R marinoscar/EnterpriseAppBase --template seam_request.yml`). Never edit platform code from Vault; work down the extension ladder first and record a stop-gap in [local-exceptions](docs/platform-adoption/local-exceptions.md).
- Link the work with `Fixes #<n>` / `Relates to #<n>` in commits and the PR ([`.github/pull_request_template.md`](.github/pull_request_template.md)). Feature and bug work only: `chore`/`docs`/`refactor` need no issue.

## MANDATORY: Worktree-Based Feature Development

The main checkout stays on `main`. Every feature or fix is developed in a Git worktree.

- Worktrees live under `worktrees/<short-name>` (git-ignored, flat names); branches are `<type>/<short-name>` (`feat/`, `fix/`). The **main agent** creates them after the issue exists: `git worktree add worktrees/<short-name> -b <type>/<short-name>`.
- All development and commits happen inside the worktree. To finish: commit, then `git worktree remove worktrees/<short-name>`; the branch remains for the PR.
- Never check out a feature branch or work on a feature in the main checkout. One worktree per branch; reuse an existing one.
- **Exception**: in a cloud session, or whenever the environment has already put you on a designated branch, work on the branch the session designates instead of creating a worktree.

## MANDATORY: Commit, Then Always Open a PR

Create clean, frequent commits, then land the work through a pull request. Assume the branch already exists and is checked out; subagents never create branches and never run git.

**Every change ships as a PR. Never merge to `main` by pushing to it.** Every change, however small, is a PR against `main`; do not wait to be asked. The order is fixed:

1. Commit the work in slices.
2. Push the branch (`git push -u origin <branch>`).
3. Open the PR against `main`, filling in `.github/pull_request_template.md` and linking its issue.
4. Merge once CI is green and nothing is outstanding.

- **Green first, merge second.** Merge when checks pass and review threads are answered, never by disabling or skipping a check. A red check this diff did not cause is said so on the PR.
- **A merged PR is finished.** Follow-up work is a fresh branch off the updated `main` and a new PR; never push onto a merged branch.
- **Commit early, commit often**: small, coherent, one intent per commit. No unrelated refactors, repo-wide formatting or dependency upgrades. If the diff feels big, split it sooner.
- **A behaviour change carries its tests** in the same commit or the next one.
- **Format** (Conventional Commits): `<type>(<scope>): <short imperative summary>`. Types: `feat`, `fix`, `refactor` (no behaviour change), `test`, `docs`, `chore`. Scopes: `api` `web` `cli` `db` `infra` `auth` `ui` `core` `jobs` `ai` `secrets` `cards` `backups` `media` `docs` `tests`.
- **Sequence**: `git status`, `git diff`, stage intentionally (`git add -p` or named files), `git commit`, `git status`.
- **Tests not run**: still commit, and say so in the body (`Notes: tests not run (DB env not available).`).

## MANDATORY: Settings UI Pattern (TARGET from E10; rule for new pages now)

Today settings are tabs (`SystemSettingsPage`: UI Settings, Feature Flags, AI, Backups, Advanced (JSON); `UserSettingsPage`). E10 replaces them with a registry-driven hub. Spec: [docs/specs/ux-refresh.md](docs/specs/ux-refresh.md); recipe: [`add-settings-page` skill](.claude/skills/add-settings-page/SKILL.md).

1. **Every new settings page is a card in a section registry** (`ADMIN_SECTIONS` in `apps/web/src/config/adminSections.tsx`, `USER_SETTINGS_SECTIONS` in `userSettingsSections.tsx`; created in E10). Append; never insert between existing cards.
2. **A settings page is never added as a new tab on an existing settings page.** Tabs only for genuinely parallel content inside one destination. Until E10 lands, a new settings surface is its own routed page, not another tab of `SystemSettingsPage`.
3. **The card's `permission` is the exact string the API controller enforces**, never invented: `system_settings:read`/`:write`, `users:read`, `allowlist:read`, `secret_types:read`, `secrets:read` (My backups), `user_settings:read`.
4. **Reuse the packaged `SettingsHub`** (`@marinoscar/platform-web/settings/ui`); never fork it.
5. **The five coupled breakpoint gates move together or not at all** (all at `sm`, 600px, never `md`): `ShellLayout` `showRail` and `<main>` `pb`, `ShellBottomNav` self-gate, `SettingsHub` `isCompactWindow`, `ShellAppBar` `isCompactWindow`. They are the platform's once E10 lands; the app must read no breakpoint of its own for them.

## MANDATORY: Every Long-Running Activity Is a Queue Job (TARGET from E5)

Design: EAB `docs/specs/job-queue.md`; recipe: [`add-job-type` skill](.claude/skills/add-job-type/SKILL.md).

1. **No long-running work outside the queue.** Anything that outlives the HTTP request or cron tick is a registered `JobHandler` with a declared `type`, enqueued through `JobsService` with an explicit `orgId`. A detached `void this.doX()`, an `@OnEvent` body that downloads or spawns, and a `@Cron` body that works inline are violations. A `@Cron` only decides whether work is due and enqueues (`enqueueHousekeepingJob`).
2. **Known exception until E5:** `apps/api/src/backups/backup-runner.service.ts` runs backups in-process (`@Cron` every minute, detached `launch()`, Postgres advisory locks). It becomes the job types `vault.backup.run` and `vault.user_backup.run`. Do not copy this pattern; it is listed in [local-exceptions](docs/platform-adoption/local-exceptions.md).
3. **Backup jobs are server-only**: the archive password and `VAULT_ENCRYPTION_KEY` never go to a worker node (no `nodeResultSchema`/`persistNodeResult`). A node never persists a job-scoped credential.
4. A job declares `profile` `{ maxRuntimeMs, maxAttempts }` or takes the default; never add `leaseMs` or `heartbeatMs`. A job `type` string is permanent once jobs of that type exist.

## MANDATORY: AI Rules

Today AI is the generic config/verify/OpenAI provider plus card extraction in `apps/api/src/ai/`. From E8 it is `AiService.forUser(userId, { orgId, feature: 'card-extract' })` of the platform.

1. **Keys never leave the server and the browser never calls a provider.** Every provider call is server-side. No route, log line, span, error or audit row carries key material; the admin AI key is stored AES-256-GCM-encrypted and write-only.
2. **Card CVV is never sent to AI and never persisted by extraction.** `POST /api/secrets/cards/extract` persists nothing, never requests or returns the CVV, and runs behind the admin toggle and the daily budget (counted from `audit_events` rows `ai.card.extract`).
3. **Card photos are user material**: egress is disclosed in the UI (`AiEgressNotice`), and fixtures use generated or placeholder images only.
4. **AI settings cards declare `feature: 'ai'`** (E10), except the card that switches AI on. A new provider SDK import stays inside its provider folder (`apps/api/src/ai/providers/<provider>/`).

## MANDATORY: Invariants that are easy to break

- **Secret values exist only as AES-256-GCM ciphertext** under `VAULT_ENCRYPTION_KEY` (`apps/api/src/common/services/crypto.service.ts`), in `secret_versions`. The same key encrypts the AI key in `system_settings` and the scheduled-backup password. **Never re-encrypt, rotate or change the key without a rehearsed migration on a restored copy.** It stays an app-owned variable after the platform migration (permanent divergence, not the platform `SECRETS_ENCRYPTION_KEY`).
- **Never log, return or persist plaintext secret values**, decrypted version data, backup passwords or API keys. Detail responses decrypt on read only.
- **Exactly one `isCurrent = true` version per secret**, enforced by the partial unique index `secret_versions_current_unique`. Update creates a new version only if data changed; rollback creates a new current version; versions are immutable.
- **Attachments are version-scoped** (`secret_attachments.secret_version_id`, optional `role` `card_front` | `card_back`). Deleting the last reference to a `storage_objects` row deletes it; a referenced object is never deleted out from under another version or secret (refcount deletion).
- **System secret types are read-only** (`apps/api/prisma/system-secret-types.ts`) whatever the permission; deleting a custom type with secrets is a 409.
- **A backup archive password is never stored in plaintext and never logged**: user "My backups" use it in memory only; the scheduled one is stored encrypted and write-only (`passwordConfigured`, never the value). `includeSystem` on a user export is a 400.
- **Export endpoints return a raw zip, not `{ data }`** (`POST /api/secrets/export`, `POST /api/admin/backups/export`), streamed, with the `X-Vault-Export-*` headers, audited as `secrets.export` / `backups.export`. Permanent; the platform `{data}` envelope must not wrap them.
- **Installed migrations are never edited or renamed** (comments inside `migration.sql` count). The seven existing ones are history. From E2 `platform.lock` proves it; `npm run db:check` fails on any byte change. Raw-SQL partial/expression indexes are intentional drift (today `secret_versions_current_unique`, `UNIQUE (secret_id) WHERE is_current = true`); never "fix" one with `@@unique` or a `findFirst` pre-check.
- **`notify()` runs after the triggering write commits**, outside any `$transaction` (TARGET from E7).
- **RLS (TARGET from E2):** the API connects as an ordinary `NOSUPERUSER NOBYPASSRLS` role that owns the tables; `app.org_id` and friends are set only with `set_config(..., true)` as the first statement of a transaction; every dump and restore carries `--enable-row-security` and `PGOPTIONS=-c app.rls_bypass=on`.
- **A backup archive is never buffered**: dumps stream into object storage and the upload and exit code are both awaited.
- **There is no `*:read_any` bypass by accident**: `secrets:read_any`/`write_any`/`delete_any` and `storage:*_any` are Admin only; a no-access read answers 404 for foreign resources.

## Architecture principles

1. **Separation of concerns**: the UI presents; the API handles all business logic and authorization.
2. **Same-origin hosting**: UI at `/`, API at `/api`, API reference (Scalar) at `/api/docs`.
3. **Security by default**: every endpoint declares `@Auth(...)` unless deliberately public (`@Public`/no `@Auth` routes are the auth, device-code, health and test-login ones).
4. **API-first**: all business logic lives in the API layer.
5. **Packages first (TARGET, E12)**: domain code moves into `@marinoscar/vault-*` packages last; hosts hold ports and shells. Domain stays in `apps/` until then.

## Security guidelines

- Secrets come from environment variables (`infra/compose/.env.example`), never from code.
- JWT access tokens are short-lived (15 min); refresh tokens are HttpOnly cookies, rotated on use. The access JWT is read only from `Authorization: Bearer`.
- Validate input on every endpoint. File uploads: size and type limits, randomized filenames; card face images are capped (default 5 MB).
- The email allowlist restricts access; `INITIAL_ADMIN_EMAIL` always bypasses it; claimed entries cannot be removed.
- Storage, AI and (later) Web Push and SMTP are configured at runtime in the admin UI and must **never** get environment variables.

## Environment variables

- [`infra/compose/.env.example`](infra/compose/.env.example) is the reference; do not duplicate it. Prose per variable: [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md), [docs/ENV-SYNC.md](docs/ENV-SYNC.md).
- `DATABASE_URL` is built at runtime from `POSTGRES_*`: use `npm run prisma:*`, never bare `npx prisma`.
- `VAULT_ENCRYPTION_KEY` is required and must not change on a database that holds secrets.
- Never add an environment variable for a runtime-configured feature. After E11, `.env.example` is generated (`npm run platform:infra:sync`); add app variables to `infra/compose/app.env.example` and never a commented `# KEY=value` line.

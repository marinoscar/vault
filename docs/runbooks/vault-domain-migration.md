# Runbook: author a domain migration (`@marinoscar/vault-db`)

Use this to change a domain table, column or index (secrets, secret types, versions, attachments, media folders, backups), to install the domain into a new host, or to recover when `vault-db check` fails. The package is `packages/vault-db` ([README](../../packages/vault-db/README.md)); the platform side of the schema is the [platform-migration skill](../../.claude/skills/platform-migration/SKILL.md).

## The two copies

The domain's fragments and migrations live in the package. The app holds installed copies that `vault-db sync` writes:

| In the package | In the app (`apps/api/prisma/`) | Rule |
|---|---|---|
| `schema/vault.<slice>.prisma` | `fragments/vault.<slice>.prisma` | Generated, header `GENERATED by vault-db sync`. Never edit, never `prisma format`. |
| `migrations/<id>/migration.sql` | `migrations/<id>/migration.sql` | Byte-identical, comments included. Never edit, never rename. |
| `migrations/manifest.json` | `vault.lock` | The manifest hashes the package copy, the lock hashes the installed copy. |
| `raw-sql-indexes.json` | `platform.lock` `rawSqlIndexes` | Merged by `sync`; `platform db drift` asserts them against `pg_indexes`. |

`apps/api/prisma/fragments/` holds nothing else now; a table that is not part of the domain gets its own `*.prisma` file there and is edited in place.

## Change a domain table

Run from `apps/api` unless noted. At most one open pull request may carry a migration; a second rebases and regenerates so its timestamp is newer.

1. **Edit the fragment in the package**, `packages/vault-db/schema/vault.<slice>.prisma` (`secrets`, `media` or `backups`). Keep every block comment. A relation to `User`, `StorageObject` or `Job` needs its back-relation in an `extend model` block of the same fragment.
2. `npm run db:compose`. It runs `vault-db sync` (the generated fragment copy updates) and then `platform db compose` (`prisma/schema/` updates).
3. `npm run prisma:migrate:dev -- --create-only --name <snake_case_name>`. This writes `prisma/migrations/<timestamp>_<name>/migration.sql` without applying it.
4. **Review the SQL.** Hand-write what Prisma cannot express: partial unique indexes, expression indexes, CHECK constraints, row-level security. A table with an `org_id` and forced RLS needs the `BEGIN; SELECT set_config('app.rls_bypass','on',true); ...; COMMIT;` wrapper ([SECURITY-ARCHITECTURE.md §18](../SECURITY-ARCHITECTURE.md#18-tenant-isolation-rls)). A migration may only touch domain tables; the only thing it may do to a host table is declare a foreign key to `users`, `storage_objects` or `jobs` (`ADD CONSTRAINT ... REFERENCES`).
5. `npx vault-db promote <timestamp>_<name> --id <name> --slice <slice>`. It refuses a migration that touches a table the domain does not own, copies the file into `packages/vault-db/migrations/<timestamp>_<name>/`, appends it to `manifest.json` (hash, slice, `requiresHostTables`) and installs it into the app under the same name, updating `prisma/vault.lock`.
6. **List any new special index.** If the migration created a partial, expression, GIN, GiST or non-btree index, `promote` prints its name. After applying the migration (step 7), copy its definition: `SELECT indexdef FROM pg_indexes WHERE indexname = '<name>';`, add `{ name, table, definition }` to `packages/vault-db/raw-sql-indexes.json` (sorted by name), and run `npx vault-db sync` so `platform.lock` gets it. A new CHECK constraint, function, trigger or generated column goes in `schema-objects.json`. A statement Prisma prints only because it cannot declare the object is excused with a `deviations` entry in `platform.lock` (platform-migration skill).
7. `npm run prisma:migrate` (or `prisma:migrate:dev`) to apply, then `npm run prisma:generate`.
8. Check:

   ```bash
   npm run db:compose:check          # prisma/schema/ equals a fresh compose
   npm run db:check                  # platform check, then vault-db check (byte identity)
   npm run db:check:database         # ledger, lock and the raw-SQL objects in the dev database
   npm run db:drift                  # replayed migrations equal the schema (needs a shadow database)
   npm run test:packages             # manifest hashes and the raw-SQL index tripwire
   ```

9. Commit together: the package copy (`packages/vault-db/schema`, `migrations`, inventories), the app copy (`prisma/fragments`, `prisma/migrations`, `prisma/schema`), `prisma/vault.lock` and `prisma/platform.lock`.

Never fix a mistake by editing an installed migration: production databases hold its checksum in `_prisma_migrations`. Write a new migration.

## Install the domain into a new host

A second host has no domain history, so it uses `stable` names. Eight of the package migrations were written before the platform baseline and touch platform tables (`add_media_folders` alters `users` and `storage_objects`; `add_media_folder_files` drops a column it added), so on a fresh database the platform history must run first: pin the platform timestamp before the domain's 2026 ids.

```bash
npx platform db sync --timestamp 2024-01-01T00:00:00Z && npx platform db compose   # platform schema and migrations first
npx vault-db sync --names stable                   # fragments, migrations, vault.lock
npx platform db compose
npx vault-db check
```

Then apply with `prisma migrate deploy` and run `npx vault-db check --database`. `packages/vault-db/test/apply.db.test.ts` runs exactly this on a scratch database.

## Migration folder names

Rule: an installed migration's folder name is a pure function of the migration; an upgrade only appends names, never renames one. A database records the name in `_prisma_migrations`, so a name that moves breaks it.

| `--names` | Installed name | Use |
|---|---|---|
| `original` | the package id (`20260403120000_add_secrets_and_versions`) | a host whose databases already ran the migrations under those names (Vault itself); the default there |
| `stable` | `<the id's 14-digit timestamp>_vault_<slug>` | a host with no domain history; the default there |
| `after-host` | `<ts>_vault_<slug>`, newest host directory + 1s | deprecated; kept for parity with `kvox-db` |

A host with a `prisma/vault.lock` keeps the policy the lock records. Upstream gap: `platform db sync` derives names from the clock or `--timestamp`; see [marinoscar/EnterpriseAppBase#992](https://github.com/marinoscar/EnterpriseAppBase/issues/992).

## When a check fails

| Code | Meaning | Fix |
|---|---|---|
| `FRAGMENT_MODIFIED`, `FRAGMENT_MISSING`, `FRAGMENT_STALE` | a generated fragment copy differs from the package | `npx vault-db sync`; edit the package file, not the copy |
| `INSTALLED_MODIFIED` | an installed `migration.sql` differs from `vault.lock` (a comment counts) | restore it from version control |
| `LOCK_ENTRY_MISSING` | the lock names a directory that is gone | restore the directory; never reinstall one that may be applied |
| `NOT_INSTALLED`, `LOCK_MISSING` | the package has migrations the app has not installed | `npx vault-db sync` |
| `PACKAGE_MIGRATION_MODIFIED` | a package migration differs from `manifest.json` | restore it; a published migration is never edited |
| `UNLISTED_RAW_INDEX`, `LISTED_INDEX_NOT_FOUND` | `raw-sql-indexes.json` and the migrations disagree | add or fix the inventory entry (step 6) |
| `FRAGMENT_DECLARES_RAW_INDEX` | a fragment declares `@@unique`, `@@index` or `@unique` for a raw-SQL index | remove the declaration; the index is intentional drift |
| `PLATFORM_LOCK_INDEX_MISSING` | `platform.lock` lacks a raw index | `npx vault-db sync` |
| `INDEX_MISSING` (with `--database`) | the database lacks a raw-SQL index | apply the missing migration |

## Rollback

Revert the pull request. The installed migration copies never moved or changed, so a database is unaffected. To undo the adoption delete `prisma/vault.lock` and the generated `prisma/fragments/vault.*.prisma`, and restore `vault.prisma` and `media-folder-files.prisma` from version control.

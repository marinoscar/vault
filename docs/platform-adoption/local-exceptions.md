# Local exceptions to the platform

Every place where Vault deviates from `@marinoscar/platform-*` on purpose, and the epic that removes it (or why it is permanent). Introduced by E0 ([#55](https://github.com/marinoscar/vault/issues/55), program epic [#54](https://github.com/marinoscar/vault/issues/54)). An exception without a row here is a bug.

## How to use this page

- **A shim in code** carries the comment `// PLATFORM-ADOPTION-SHIM(<epic or issue>)`. List them with `grep -rn "PLATFORM-ADOPTION-SHIM" apps/api/src apps/web/src`.
- **A deviation in the database** is an entry under `deviations` in `apps/api/prisma/platform.lock` (exists from E2).
- **The PR that removes an exception deletes its row**, together with the marker and any lock deviation or allowlist entry it names.
- A new exception adds a row in the same PR, with the epic or issue that removes it. If none exists, file one. A platform gap is a seam request on marinoscar/EnterpriseAppBase first.

## Deploy note (E3.2: identity is now the platform's)

The deploy freeze that the legacy role shim required is **lifted**: a contributor or viewer now gets its permissions from the platform's membership-role path, not from `user_roles`. What the operator must rehearse on a restored copy before the first deploy of E3.2 ([database-baseline runbook, section 6](../runbooks/database-baseline.md#6-migrate-seed-verify-rehearsal-copy)):

1. `npm run prisma:migrate` then **`npm run prisma:seed`**. The seed is not optional: it registers `secrets:*`, `secret_types:*` and `media:*` as **org-scoped** permissions, grants them to `org_admin`, `contributor` and `viewer`, and removes the now stale `admin` grants of them. Without it `org_admin` holds no secret permission.
2. Sign in with an existing contributor, a viewer and an administrator (device login with `vaultcli` too): `/api/auth/me` must list `secrets:*` for the first two and the `*_any` permissions only for the administrator.
3. Existing sessions survive: refresh tokens, PATs and device codes use the same sha256 hashing; access tokens issued before the deploy carry no `org` claim and are accepted for one access-token lifetime after the process starts. `JWT_SECRET` must not change; restart every API replica (the principal cache is per process).
4. New optional variables (all defaulted): `DEVICE_TOKEN_EXPIRY_DAYS`, `DEVICE_PAT_EXPIRY_DAYS`, `AUTH_PRINCIPAL_CACHE_TTL_SECONDS`, `TENANCY_MODE` (leave unset: single-organization mode).

## E5.2: backups as queue jobs (done)

Done in [#82](https://github.com/marinoscar/vault/issues/82). What shipped, for the next reader:

1. **Handlers** (`apps/api/src/backups/jobs/`, self-registering, server-only: no `nodeResultSchema` / `persistNodeResult`): `vault.backup.run` (system job, `orgId` null, label "Secrets backup") and `vault.user_backup.run` (`subjectType 'user'`, label "My backup"), both `profile { maxRuntimeMs: 30 * 60_000, maxAttempts: 1 }`. The archive build lives in `BackupArchiveService` (streams into storage, never buffered; the writer and the upload are both awaited); the run lifecycle in `BackupRunnerService`; the routes queue through `BackupQueueService`. Both type strings are in `PINNED_JOB_TYPES`.
2. **Password.** A user archive password travels in `jobs.payload` only as `CryptoService` ciphertext (`passwordEncrypted`); the handler decrypts it in memory, never logs it, and removes the ciphertext from the row when the run settles (success or failure). `test/backups/backup-jobs.db.spec.ts` asserts the payload, the logs, the audit rows and the run rows.
3. **Schedule tick.** `backups/backup-schedule.task.ts` is enqueue-only: it claims the due slot (compare-and-set on `next_run_at`) and calls `JobsService.enqueue`; the handler writes the scheduled run's `backup_runs` row. If the enqueue fails the slot is put back.
4. **Dedup replaces advisory locks.** The queue's active-dedup key (`buildDedupKey(type, subjectType, subjectId)`) is the "is a backup running" check: one active system backup, one per user. A manual run writes the `jobs` row and the `backup_runs` row in one transaction (`enqueueWithin`); a dedup conflict rolls it back and is `409` on `POST /admin/backups/run` and `POST /backups/me`. A scheduled enqueue that collides collapses silently. Deleted: the advisory locks, the heartbeat, `failStaleRuns`, `inFlight`/`waitForIdle`, `launch()`, `backup-runner.stale.spec.ts`, the `rawSqlAllowlist` entry and the no-inline-timers exemption.
5. **Migration.** `20261102140000_backup_runs_job_id`: `backup_runs.job_id UUID NULL REFERENCES jobs(id) ON DELETE SET NULL` plus an index (app fragment `vault.prisma`, with `extend model Job { vaultBackupRuns BackupRun[] }`), and a one-off sweep that marks rows still `running` with no job (started by the removed in-process runner) as failed. `heartbeat_at` stays in the table, unwritten (expand/contract). The status the API shows is derived: a row still `running` whose job ended `failed` (a crash or reaped lease) is reported as `failed`, and can be deleted.
6. **Conformance.** The `backups/backup-runner.service.ts` entry of `CRON_EXEMPTIONS` is deleted; `minCronFiles` is the remaining exemption plus the schedule task. The RBAC matrix stubs `BackupQueueService` instead of the runner.

## Permanent divergences

| Divergence | Where | Why it stays |
|---|---|---|
| **`VAULT_ENCRYPTION_KEY` is an app-owned key for secret ciphertext** (AES-256-GCM via `CryptoService`), separate from the platform's `SECRETS_ENCRYPTION_KEY` that encrypts runtime-configured credentials | `apps/api/src/common/services/crypto.service.ts`; `secret_versions`, the scheduled-backup password | Live production data is encrypted under it. Pinned by `test/export/raw-zip.integration.spec.ts` |

## RLS readiness: paths that needed an org scope in E2.3 (done)

# Local exceptions to the platform

Every place where Vault deviates from `@marinoscar/platform-*` on purpose, and the epic that removes it (or why it is permanent). Introduced by E0 ([#55](https://github.com/marinoscar/vault/issues/55), program epic [#54](https://github.com/marinoscar/vault/issues/54)). An exception without a row here is a bug.

## How to use this page

- **A shim in code** carries the comment `// PLATFORM-ADOPTION-SHIM(<epic or issue>)`. List them with `grep -rn "PLATFORM-ADOPTION-SHIM" apps/api/src apps/web/src`.
- **A deviation in the database** is an entry under `deviations` in `apps/api/prisma/platform.lock` (exists from E2).
- **The PR that removes an exception deletes its row**, together with the marker and any lock deviation or allowlist entry it names.
- A new exception adds a row in the same PR, with the epic or issue that removes it. If none exists, file one. A platform gap is a seam request on marinoscar/EnterpriseAppBase first.

## Deploy note (E3.2: identity is now the platform's)

The deploy freeze that the legacy role shim required is **lifted**: a contributor or viewer now gets its permissions from the platform's membership-role path, not from `user_roles`. What the operator must rehearse on a restored copy before the first deploy of E3.2 ([database-baseline runbook, section 6](../runbooks/database-baseline.md#6-migrate-seed-verify-rehearsal-copy)):

1. `npm run prisma:migrate` then **`npm run prisma:seed`**. The seed is not optional: it registers `secrets:*`, `secret_types:*` and `media:*` as **org-scoped** permissions, grants them to `org_admin`, `contributor` and `viewer`, and removes the now stale `admin` grants of them. Without it `org_admin` holds no secret permission.
2. Sign in with an existing contributor, a viewer and an administrator (device login with `vaultcli` too): `/api/auth/me` must list `secrets:*` for the first two and the `*_any` permissions only for the administrator.
3. Existing sessions survive: refresh tokens, PATs and device codes use the same sha256 hashing; access tokens issued before the deploy carry no `org` claim and are accepted for one access-token lifetime after the process starts. `JWT_SECRET` must not change; restart every API replica (the principal cache is per process).
4. New optional variables (all defaulted): `DEVICE_TOKEN_EXPIRY_DAYS`, `DEVICE_PAT_EXPIRY_DAYS`, `AUTH_PRINCIPAL_CACHE_TTL_SECONDS`, `TENANCY_MODE` (leave unset: single-organization mode).

## E5.2 plan: backups as queue jobs

Everything E5.2 ([#82](https://github.com/marinoscar/vault/issues/82)) needs is mounted by E5.1: `JobsService`, `JobHandlerRegistry`, `enqueueHousekeepingJob`, the worker, the Jobs admin routes and the conformance exemption it deletes.

1. **Handlers** (`apps/api/src/backups/jobs/`, self-registering in `onModuleInit`, server-only: no `nodeResultSchema` / `persistNodeResult`): `vault.backup.run` (`orgId: null`, `profile { maxRuntimeMs: 30 * 60_000, maxAttempts: 1 }`, label "Secrets backup") and `vault.user_backup.run` (`subjectType 'user'`, `subjectId` = user id, same profile, label "My backup"). The extraction of the archive build from `BackupRunnerService` into a plain service both handlers call keeps the zip streaming (never buffered). Add the two strings to `PINNED_JOB_TYPES` in `test/jobs/job-type-snapshot.spec.ts`.
2. **Password handling.** The user archive password goes into `jobs.payload` only as `CryptoService` ciphertext; the handler decrypts in memory and never logs it. A log-spy test and a `jobs.payload` assertion prove it.
3. **Schedule tick.** `backups/backup-schedule.task.ts`: `@Cron(EVERY_MINUTE)` decides whether the schedule is due (claim moves `next_run_at`) and calls `enqueueHousekeepingJob`; no work inline.
4. **Dedup replaces advisory locks.** `dedupKey` `vault.backup.run:system` and `vault.user_backup.run:<userId>`; a dedup conflict is HTTP 409 on `POST /admin/backups/run` and `POST /backups/me`. Delete `pg_advisory_xact_lock` use (the `rawSqlAllowlist` entry in `test/conformance.spec.ts`), the heartbeat, `failStaleRuns`, `inFlight`/`waitForIdle`, `launch()` and `backup-runner.stale.spec.ts`.
5. **Migration (the one open migration PR).** App fragment `backup_runs.job_id UUID NULL REFERENCES jobs(id) ON DELETE SET NULL` + index; `extend model Job { vaultBackupRuns BackupRun[] }`. `heartbeat_at` stays unused (expand/contract). One-off sweep for rows still `running` at deploy time. Status shown to the UI is derived from the job.
6. **Delete the exemption**: remove the `backups/backup-runner.service.ts` entry of `CRON_EXEMPTIONS` (the suite then requires `minCronFiles` to drop by one), the marker and this row. Update the `BackupRunnerService` override in `test/rbac/vault-rbac-matrix.integration.spec.ts` (routes enqueue instead).
7. **Tests**: scheduled, manual and user backups through the worker (`JOBS_WORKER_MODE=all`, as `test/jobs/jobs-runtime.db.spec.ts`), retention keeps the newest N, dedup 409, password absent from the payload and logs, `server-only-types.spec.ts` still green.

## RLS readiness: paths that needed an org scope in E2.3 (done)

**Done in E2.3.** Every path below now runs through `runInDefaultOrg` / `defaultOrgClient`; `test/rls/storage-isolation.db.spec.ts` proves it as `vault_app`. Original note: RLS on `storage_objects` and `storage_object_chunks` is forced but inert while the API is a superuser. When E2.3 moves the API to `vault_app` (`NOSUPERUSER NOBYPASSRLS`), every read or write of those tables, and of every table joined through them (`secret_attachments` includes, `media_folder_files`), must run inside `PrismaService.forOrg(orgId)` / `runInOrg(orgId, fn)` for the default organization (never a session-level `SET`, and `runInOrg`, not `forOrg`, inside `$transaction`). Otherwise reads return nothing and inserts fail the policy check, which looks like data loss. Paths found by grepping `storageObject`, `storage_objects`, `mediaFolderFile` and the `include`s of `storageObject`:

- `storage/objects/objects.service.ts`, `storage/processing/object-processing.service.ts`, `storage/tasks/storage-cleanup.task.ts`
- `media/media.service.ts`
- `secrets/secrets.service.ts` (the attachment `$transaction` with `FOR UPDATE`), `secrets/export/*` (`secrets-export.service.ts`, `media-export.ts`)
- `backups/backup-runner.service.ts` (size estimate, media and attachment streaming), `backups/my-backups.service.ts`
- `ai/card-extract.service.ts` if it reads attachments
- `prisma.service.ts` `cleanDatabase()` is unaffected (`TRUNCATE` ignores RLS), but a test that needs the default organization must re-insert it (the truncate also wipes `organizations`).

# Local exceptions to the platform

Every place where Vault deviates from `@marinoscar/platform-*` on purpose, and the epic that removes it (or why it is permanent). Introduced by E0 ([#55](https://github.com/marinoscar/vault/issues/55), program epic [#54](https://github.com/marinoscar/vault/issues/54)). An exception without a row here is a bug.

## How to use this page

- **A shim in code** carries the comment `// PLATFORM-ADOPTION-SHIM(<epic or issue>)`. List them with `grep -rn "PLATFORM-ADOPTION-SHIM" apps/api/src apps/web/src`.
- **A deviation in the database** is an entry under `deviations` in `apps/api/prisma/platform.lock` (exists from E2).
- **The PR that removes an exception deletes its row**, together with the marker and any lock deviation or allowlist entry it names.
- A new exception adds a row in the same PR, with the epic or issue that removes it. If none exists, file one. A platform gap is a seam request on marinoscar/EnterpriseAppBase first.

## Permanent divergences

| Divergence | Where | Why it stays |
|---|---|---|
| **`VAULT_ENCRYPTION_KEY` is an app-owned key for secret ciphertext** (AES-256-GCM via `CryptoService`), separate from the platform's `SECRETS_ENCRYPTION_KEY` that encrypts runtime-configured credentials | `apps/api/src/common/services/crypto.service.ts`; `secret_versions`, the scheduled-backup password | Live production data is encrypted under it. Changing or rotating it without a rehearsed migration makes every secret unreadable. Both keys coexist after E4; the platform never sees secret values |
| **Export endpoints return a raw streamed zip, not the `{ data }` envelope** | `POST /api/secrets/export`, `POST /api/admin/backups/export` (headers `X-Vault-Export-*`) | A browser/CLI download of an encrypted archive, audited as `secrets.export` / `backups.export`. They bypass the host envelope and any platform response wrapper: the two handlers take `@Res()` (no passthrough) and call `reply.send(stream)`, because the platform `TransformInterceptor` wraps a returned `StreamableFile` in `{ data }`. Pinned by `test/export/raw-zip.integration.spec.ts` |
| **Logical secret backups are not the platform `db-backup`** | `apps/api/src/backups/` | They produce password-protected AES-256 zips of secrets (with optional versions, attachments, media), not `pg_dump` archives. E9 adds the platform `db-backup` slice alongside; both coexist, with distinct storage prefixes (`user-backups/<userId>/` for My backups) |
| **Raw-SQL partial unique index `secret_versions_current_unique`** (one current version per secret) | `20260403120000_add_secrets_and_versions` | Intentional drift; listed in the raw-SQL index list from E2 |
| **System secret types are read-only code-seeded data** | `apps/api/prisma/system-secret-types.ts` | Domain rule independent of the platform |
| **Card extraction rules**: CVV never requested, nothing persisted, daily budget from `audit_events` | `apps/api/src/ai/card-extract.*` | Domain privacy rule; stays when AI moves to `AiService.forUser` |
| **Domain permission strings** (`secrets:*`, `secret_types:*`, `media:*`; `*_any` Admin only) | `apps/api/src/common/constants/roles.constants.ts` | Registered through the app's permission manifest; names are persisted in role seeds and tokens |

## Drift allowlist and lock deviations

`apps/api/prisma/platform.lock` is the machine-readable record. `npm run db:drift` is green (no allowlist is needed: every difference between the migrations and the composed schema is either absent or a raw-SQL index listed below).

**Raw-SQL index** (`rawSqlIndexes`): `secret_versions_current_unique`, `CREATE UNIQUE INDEX ... ON public.secret_versions USING btree (secret_id) WHERE (is_current = true)`. Intentional drift; never `@@unique` it. Asserted by B4, by `platform db drift`, and offline by the `app-schema-objects` conformance test (`test/prisma/platform-db-conformance.spec.ts`).

**Baseline deviations** (`deviations`; produced by `scripts/baseline-deviations.mjs` from the dry-run report, which refuses anything it cannot prove). They exist because the live production database differs from the platform history **at version 0002**; they are not exceptions to the schema going forward:

| Id | Statements | What it declares | Removal |
|---|---|---|---|
| `vault:pre-0005-uuid-defaults` | 11 | `ALTER TABLE "<t>" ALTER COLUMN "id" DROP DEFAULT` on `allowed_emails`, `audit_events`, `device_codes`, `permissions`, `refresh_tokens`, `roles`, `storage_object_chunks`, `system_settings`, `user_identities`, `user_settings`, `users`. Vault's `20260403235813_add_media_folders` did this early; platform 0005 re-runs it as a no-op | Stays as a record while any database was baselined from the old history |
| `vault:storage-media-folder-id` | 3 | `storage_objects.media_folder_id` (printed with the twelfth early `DROP DEFAULT`, on `storage_objects`), `storage_objects_media_folder_id_idx`, `storage_objects_media_folder_id_fkey` | Gone from every database once `20261102130000_add_media_folder_files` has run; the entry stays as the record for the pre-migration gate |
| `vault:domain-schema` | 35 | Every table, index and foreign key of `secret_types`, `secrets`, `secret_versions`, `secret_attachments`, `media_folders`, `backup_schedules`, `backup_runs` | Permanent record: domain tables, not a change to a platform table |
| `vault:media-folder-files` | 5 | The `media_folder_files` table, its two indexes and two foreign keys, as the diff shows them after that migration ran | Permanent record |

## RLS readiness: paths that needed an org scope in E2.3 (done)

**Done in E2.3.** Every path below now runs through `runInDefaultOrg` / `defaultOrgClient`; `test/rls/storage-isolation.db.spec.ts` proves it as `vault_app`. Original note: RLS on `storage_objects` and `storage_object_chunks` is forced but inert while the API is a superuser. When E2.3 moves the API to `vault_app` (`NOSUPERUSER NOBYPASSRLS`), every read or write of those tables, and of every table joined through them (`secret_attachments` includes, `media_folder_files`), must run inside `PrismaService.forOrg(orgId)` / `runInOrg(orgId, fn)` for the default organization (never a session-level `SET`, and `runInOrg`, not `forOrg`, inside `$transaction`). Otherwise reads return nothing and inserts fail the policy check, which looks like data loss. Paths found by grepping `storageObject`, `storage_objects`, `mediaFolderFile` and the `include`s of `storageObject`:

- `storage/objects/objects.service.ts`, `storage/processing/object-processing.service.ts`, `storage/tasks/storage-cleanup.task.ts`
- `media/media.service.ts`
- `secrets/secrets.service.ts` (the attachment `$transaction` with `FOR UPDATE`), `secrets/export/*` (`secrets-export.service.ts`, `media-export.ts`)
- `backups/backup-runner.service.ts` (size estimate, media and attachment streaming), `backups/my-backups.service.ts`
- `ai/card-extract.service.ts` if it reads attachments
- `prisma.service.ts` `cleanDatabase()` is unaffected (`TRUNCATE` ignores RLS), but a test that needs the default organization must re-insert it (the truncate also wipes `organizations`).
